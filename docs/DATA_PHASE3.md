# 第三阶段：数据层优化与恢复验证

2026-09-22。保留 Go + SQLite，继续单个写入连接。当前真实库与百万级独立夹具均不足以支持“立即迁移 PostgreSQL”的结论。本阶段不改变结算倍率、金额精度或已入账历史，不部署第二个机器人消费者。

## 代码变化

- 本期控制页在 SQL 中只读取最近200笔注单，再保持原来的时间/id升序展示；不再读取整期后丢弃大部分结果。
- 增加本期注单、玩家排序、待结算冻结及账户流水的索引。未完成消息计数使用状态等值索引，避免扫描全部已发送历史。
- 数据库版本升至 **6**：从不可变 `entries` 一次性建立 `daily_game_totals`。SQLite触发器在同一事务内增量更新游戏盈亏；失败回滚和幂等重试不会重复累计，人工调分不计入游戏统计。日界线仍为北京时间，原始流水始终是核对依据。
- 玩家模式对账按账户汇总冻结，不再逐条加载所有待结算注单，不再执行并丢弃旧双边账本的批次检查；旧双边模式仍保留批次对账。
- 服务增加一个独立只读连接，仅用于完整对账。显式读事务提供一致快照，避免占用业务写入连接的互斥锁。没有读副本或写连接池；只读连接不执行checkpoint。`/api/operations` 增加 `audit_database` 指标；原 `database` 仍指业务连接。
- 新增离线工具 `rift-dbcheck -db 备份文件`：检查文件完整性、外键、余额与流水、冻结、逐笔 `balance_after`、日汇总及队列状态；支持版本5和6。不会运行初始化/迁移、启动HTTP或Telegram、改变发送中状态。

独立备份使用只读 immutable 模式，适用于已生成且不再改动的快照，不能用于正在写入的库。工具拒绝有相邻WAL/回滚日志的文件。Docker验证脚本仅挂载一个只读备份，禁用网络，不挂载正式数据卷。实现依据：[SQLite只读WAL说明](https://www.sqlite.org/wal.html#read_only_databases)、[immutable URI约束](https://www.sqlite.org/uri.html)。正式库对账使用普通只读连接和WAL快照，不使用 immutable。

## 可复现的规模测试

本机 WSL Linux、Go1.23、SQLite3.45.1、Intel i5-8259U。夹具构造不计入计时，每项3次，是诊断基准，不是容量承诺。旧版基线为 `88611ae`，使用同一份 `data_benchmark_test.go` 在独立源码目录运行。合成历史仅用于查询诊断，完整业务与恢复检查使用另一个经真实HTTP创建的数据库。

1000名玩家、10万历史注单/流水/已发消息、1万本期注单：

- 本期状态：85.09ms → **3.40ms**；分配约17.77MB → 0.64MB。
- 玩家首页50人：44.03ms → **1.96ms**。
- 完整对账：382.52ms → **19.17ms**；分配约56.65MB → 1.57MB。

1万名玩家、100万历史注单/流水/已发消息、10万本期注单：优化后本期状态 **8.01ms**，玩家首页 **16.60ms**，完整对账 **240.28ms**。这些不是单次结算10万注的耗时，也不是机器人端到端延迟。

原始记录：[旧版10万](test-artifacts/phase3-before-100k.txt)、[新版10万](test-artifacts/phase3-100k.txt)、[新版百万](test-artifacts/phase3-million.txt)。

另一个真实HTTP隔离测试含16个测试账户、100万条带正确逐笔余额的历史游戏流水、8并发客户端。288次请求中包含64次上分及同键重放、40次完整对账，其余为统计/状态查询。全部余额与整数基准一致，日汇总与游戏流水一致，对账通过。计时3.572秒；上分加重放这一组两次请求P95为88.48ms，玩家列表P95为40.92ms，对账P95为706.00ms。对账在一个只读连接上串行，排队计入请求耗时；不是无限并行。数据生成和最终核验不计入吞吐。[原始记录](test-artifacts/phase3-load.json)。

## 恢复验收

`restore_drill.py` 通过真实HTTP建立三位小数上分、结算、另一笔冻结注单和自定义模板；在服务运行中用SQLite backup API创建一致快照，离线验证后恢复到全新目录，清除Telegram环境变量，不复制机器人配置。确认：

- 余额1120.200、冻结100.001、赔率、活动期、流水、模板和更新offset恢复。
- 上分/结算的旧幂等键重放不再次入账。
- 备份之后增加的0.001不混入已恢复快照。
- 离线验证不改备份、不发送消息；恢复服务将中断发送标记UNKNOWN，待发消息保留且未尝试发送。

[恢复演练原始记录](test-artifacts/phase3-restore.json)。回归还覆盖北京时间日界线、增量统计回滚/重复、旧版回填、迁移失败原子回滚、篡改日汇总/历史余额检测、只读文件/特殊字符路径、只读快照中业务连接继续提交。全包race/vet、HTTP重启验收及11项Node测试通过；immutable模式与迁移失败的后续专项race检查通过。

服务器实际快照另做只读复制核验：版本5，4账户、10期、11注单、14流水、134条SENT任务，数据库397312字节。完整性、外键、余额、冻结、逐笔余额全部通过，副本及原备份SHA256一致。备份为 `backups/rift-ledger-20260922T024340Z-519533.db`，隔离副本/记录在服务器 `/root/rift-phase3-restore-20260922/`。没有启动该副本的机器人，没有覆盖正式库。生产当时仍运行 `88611ae`。

## 升级与回退

```bash
cd /opt/rift-ledger/rift-ledger-go
bash scripts/update.sh
bash scripts/data-diagnostics.sh
bash scripts/backup.sh
# 用刚输出的实际备份文件名替换下面的路径
bash scripts/verify-backup.sh backups/实际备份文件.db
```

`update.sh` 在重启前生成旧库备份。首次启动版本6时，新增索引及历史日汇总会在事务中完成；数据越大，首次启动时间和额外磁盘需求越大，应先在副本演练。没有重新缩放三位小数，也不重新结算历史。

旧程序不能读取版本6。**不要仅回退代码或镜像后继续打开新库。** 回退需要停写、保留当前库和日志、选择升级前备份，核实备份之后的账目以及Telegram offset/消息送达。恢复旧快照可能丢失后续入账或重复发消息，因此不提供直接覆盖正式库的一键恢复。

数据库备份包含模板和上传图片，**不包含** `.env`、`runtime-settings.json` 和英雄缓存；配置需另行受限备份。验证工具证明快照内部一致，不能证明它包含所有最近交易，也不能证明备份后消息尚未发送。

本地Docker构建尝试在拉取基础镜像时因Docker Hub连接超时失败；未进入编译步骤。Go二进制、恢复脚本和只读检查已验证，但新增Docker封装尚未运行验收。本阶段没有更新生产服务。

## 下一次数据库选型的条件

保留SQLite，不做历史删除/归档或自动VACUUM。观察目标机器高峰的业务锁等待、写入延迟、对账读事务时长、WAL大小和磁盘余量；长读快照可能推迟checkpoint，应避免持续无间隔全量对账。超过业务可接受延迟时，先复现具体查询/写事务，而不是仅凭库文件大小迁移。只有单写入吞吐或多实例容灾需求确实超出当前设计，才进入PostgreSQL影子验证、逐笔对账、停写切换和回退方案。当前仍未验证24小时持续负载、磁盘满/断电或多实例容灾。
