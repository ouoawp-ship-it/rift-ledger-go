# 性能与稳定性升级：第一阶段

2026-09-22。本阶段完成运行观测、可复现基准、统计查询优化、发送调度优化和后台导航调整。继续采用 Go 模块化单体、SQLite 单写入连接和内嵌网页；没有迁移 PostgreSQL、接入真实 Telegram 压测或部署多实例。

## 已修复的问题

- 玩家列表的“上期盈亏”在每笔历史下注中重复查找最后结算时间，数据增多后会长时间占用数据库锁。现在先定位该玩家最近的已结算期次，再汇总该期下注，并新增账户/期次、账户/结算时间及游戏流水时间索引。
- 原查询按秒级时间汇总，两期在同一秒完成时可能混算“上期盈亏”。现在按期次区分，同秒使用期次创建顺序裁决；历史下注与余额不修改。
- 按钮应答的网络请求原先与接收循环串行，慢应答可能阻挡后面的更新。现在使用容量128的独立应答队列和2个工作协程，每次最多等待3秒；业务仍按更新顺序提交，满队列会记录警告。
- 发送工作协程原先每发一条固定暂停1秒。现在由共享调度器控制发送间隔，并在事务提交后唤醒发送器；空队列保留500毫秒轮询，处理重试到期和遗漏唤醒。

发送调度目标为总计至少间隔50毫秒、同一私聊至少1秒、同一群至少3秒；持久队列中的冷却时间仍然生效。它们是本项目的保守调度参数，不是 Telegram 吞吐量承诺。429继续遵守服务端 retry_after，结果未知仍需核实，不能为了“速度”盲目重复公示。

## 运行检查页面

新增需要管理员鉴权的 `GET /api/operations`，页面每5秒刷新：

- **接收**：长轮询是否正常、连接是否过期。与“发送成功”分开判断。
- **业务**：本次启动处理次数、失败次数、最后失败更新编号、最近/最大耗时。下游处理失败不会被接收正常掩盖。
- **发送**：待发、发送中、失败/未知数量，以及最老未完成任务的年龄。达到60秒显示等待较长，有失败/未知任务显示需要处理；这不表示所有会话都停止。
- **数据库**：外层查询/事务的平均锁等待、平均执行耗时及最大值，用于区分排队和实际执行成本。

业务和耗时计数在进程重启后归零；数据库指标包括启动初始化，属于累计观测，不是滚动窗口或长期监控历史。读取失败会清掉旧的绿色状态。账目正确性仍使用只读对账；当前不接入 Prometheus、外部告警平台或按业务分类的直方图。

后台同时加入深色侧栏、浅色内容区、桌面折叠导航和可关闭的已访问页面标签。切换标签保留页面已有的表单输入；本次没有迁移到 Vue，也没有加入新的前端打包依赖。

## 可复现检查

需要 Linux、Go 1.23、C编译器、SQLite开发库、Python3；前端测试还需要Node.js。在源码根目录运行：

```bash
bash scripts/test.sh
node --test scripts/api_client_test.cjs scripts/bot_connection_test.cjs scripts/money_test.cjs
go test ./internal/app -run '^$' -bench '^BenchmarkPlayerSummary$' -benchtime=3x -count=1
python3 scripts/load_test.py
```

`load_test.py` 自行编译并启动仅监听回环地址的临时服务，清除 Telegram 环境变量，使用随机密钥和临时数据库。不能传入正式网址或生产Token，不会连接机器人。结束后停止该临时服务并清理自己的临时目录。

### 玩家列表基准

本机 WSL Linux、Go 1.23.0、SQLite 3.45.1、Intel i5-8259U；500名合成玩家、100个历史期次、50,000笔下注，查询首页50名玩家。构造数据不计入计时，优化前后使用同一测试夹具和机器，每轮3次查询。

- 优化前：`3050555167 ns/op`，约 **3.05秒/次**，`59730 B/op`、`1440 allocs/op`。
- 优化后：`6810567 ns/op`，约 **6.81毫秒/次**，`59869 B/op`、`1442 allocs/op`。

这是指定查询的小样本诊断基准，合成下注并不构造完整账本，不用于账本验收；不能据此宣称整个系统提速相同倍数。

### 并发 HTTP 与账本验收

2026-09-22本地最终记录：8个并发客户端，288次计时区间内的HTTP请求，2.806秒，约102.65请求/秒。启动、种子数据与最终验收不计入吞吐量。64次独立上分各重放一次，另有4类只读请求各40次，以固定随机种子交错执行。

- 上分并重放：64组，P50 **182.36ms**、P95 **280.23ms**、最大330.89ms。每组包含两次串行HTTP请求，不是单次上分延迟。
- 玩家列表：P95 **162.58ms**；状态读取：P95 **123.15ms**。
- 机器人状态：P95 **161.93ms**；运行观测：P95 **122.18ms**。
- P95使用最近秩定义。数据库累计330个外层操作，最长锁等待194.42ms、最长执行117.55ms；计数也包括初始化和验证操作，与计时区间不完全相同。
- 16名玩家最终余额全部为 **1004.004**，重复请求没有重复上分，账本只读对账通过。

该短测证明这组并发场景下的完整响应和幂等结果，不代表持续吞吐上限。临时SQLite位于本机文件系统，服务器磁盘、DNS、网络和 Telegram 限流都未包含在测量中。数据库仍有锁竞争，后续应先观察生产量级和慢操作，再决定读连接/统计汇总或数据库迁移。

## 回归结果与后续顺序

已通过全包 `go vet`、`go test -race -count=1 -cover ./...`、真实HTTP重启恢复脚本、11项Node.js测试。新增覆盖同秒跨期盈亏、三段健康状态、提交后唤醒、全局/会话限速、慢按钮应答不阻挡下一次业务更新、锁等待统计。浏览器检查覆盖桌面/390px布局、导航折叠、标签关闭、赔率草稿切换保留。

后续按观测结果推进：

1. 在独立测试机器人上验收收发，结合实际消息量做持续负载、断网/429和恢复演练，记录端到端延迟及积压恢复时间。
2. 如果统计量继续增长，针对慢查询建立汇总/增量统计，并验证其与不可变流水的一致性。后台按页面推进组件化，单独验证表单与幂等请求。
3. 如果优化后数据库锁等待仍持续超出业务目标，再设计 PostgreSQL 迁移、备份恢复及回滚演练。
4. 只有明确可用性目标、单点故障损失与接管规则后，才实现多实例容灾；不得直接扩大同一Bot的接收实例数。

升级时沿用 `bash scripts/update.sh`；本阶段仅增加索引，不重新缩放金额或重算历史。旧库首次建立索引可能增加启动时间。尚未在用户服务器执行更新，未做真实Telegram联调、Docker镜像验收、长期压力测试或灾难恢复演练。
