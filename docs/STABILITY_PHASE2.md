# 第二阶段：收发故障恢复与持续负载验收

2026-09-22。代码及隔离故障测试；真实服务器和独立测试机器人验收仍待执行。没有读取正式Token、发送真实群消息或操作正式账本。

## 本阶段改动

### 统一处理发送限流

以前429仅让当前任务等候，其他发送协程仍可能继续请求。现在文字、图片和群权限任务统一处理429：

- 立即暂停共享发送调度器；同一事务将任务退回待发送，并将全局恢复时间写入SQLite。
- 重启仍遵守恢复时间，多次限流取较晚的截止时间，不缩短先前等待。
- 已领到任务、尚未发送的工作协程，在网络请求前再次检查暂停；已在网络中传输的请求无法撤回。
- 等待按秒向上取整，避免亚秒边界导致提前重试。后台显示“限流等待”及预计恢复时间，等待结束自动继续。

`retry_after` 表示重新请求前需要等待的秒数，参见 [Telegram ResponseParameters](https://core.telegram.org/bots/api#responseparameters)。API并不在该字段中标明限流范围，因此本项目选择保守暂停所有出站任务；这是本项目取舍，并非所有429都代表全局限流。这样可能延后无关会话及群权限恢复，但避免其他协程继续加重限制。接收和业务事务继续运行。

### 网络恢复与结果保存

- 连续轮询网络/服务错误按5、10、20、30秒退避，成功后重置；Telegram要求更长的429等待时遵守更长时间。401、409、Webhook或身份冲突仍需处理，不能通过抢占接收器解决。
- 已确认未发出的DNS/连接失败继续按持久任务重试；响应截断、未知送达或5xx发送结果不盲目重发。
- 网络返回后，若本地保存发送结果短暂失败，保留结果并只重试数据库操作：最多4次，间隔100、200、400毫秒，不重新发送消息。持续磁盘/数据库故障仍会保留发送中状态并记录错误；修复存储后重启，核实未知任务。
- 大于2MiB的Telegram响应及异常巨大的等待值不接受为成功，避免截断边界或时长溢出造成错误确认。

此次沿用数据库版本5，仅在meta中保存发送恢复时间，不重算余额、下注、历史结算或赔率。

## 复现与测试覆盖

```bash
bash scripts/test.sh
node --test scripts/api_client_test.cjs scripts/bot_connection_test.cjs scripts/money_test.cjs
bash scripts/test-telegram-soak.sh 300
```

持续测试需要Linux、Go/C/SQLite开发依赖，允许60至600秒，默认300秒；它启动本地模拟Telegram服务和临时数据库，不能传正式网址或Token。正常Go测试默认跳过持续场景，因此不会让Docker构建自动增加5分钟等待。

持续场景每秒产生10条个人查询更新，轮流进入40个模拟私聊。运行真实接收循环、业务去重、数据库事务和4个带限速的发送工作协程；每个非空接收批次额外重复一次更新。过程中注入一次503、一次429（等待2秒）、一次发送前DNS故障，以及一个延迟300毫秒的会话。停止输入后，最多等待60秒检查全部回复和offset。

独立回归还覆盖：限流跨会话/重启生效、已领取任务再检查、较短限流不能覆盖较长限流、发送结果落库短暂失败不重复发消息、DNS恢复、接收503后重放去重、响应超限。原有未知送达、发送中断重启、图片降级、群权限恢复及账本幂等测试继续保留。

本地60秒预检结果：600条更新、600条成功回复，采样待发峰值18，输入停止后7.325秒清空积压；端到端P50为736.314ms、P95为4819.273ms、最大7389.726ms。延迟从模拟更新产生开始，到本地模拟服务确认发送计算，包含注入故障的等待；不是纯网络延迟。

5分钟最终验收通过，完整输出见 [持续故障测试日志](test-artifacts/phase2-soak.txt)：

- 300秒内产生3000条唯一更新，最终3000条回复全部发送，持久去重与接收offset核对一致；没有重复发送。
- 每秒采样的待发峰值29条，输入停止后102ms清空剩余队列。
- 端到端P50为43.795ms、P95为3138.450ms、最大6736.601ms，包含故障和限流等待。
- Go竞态检测通过，测试总耗时300.51秒（含准备及收尾）。

全包go vet、race回归、真实HTTP/重启恢复验收及11项Node.js测试均通过。浏览器验证了限流状态和预计恢复时间的显示。诊断脚本通过shell语法检查，尚未在用户Docker环境执行。

测试运行在WSL开发机，不能推导真实Telegram吞吐上限或长期可用率。60秒预检与5分钟测试期间本机其他测试负载不同，延迟不能用于直接比较性能提升；持续5分钟也不等于24小时稳定性验证。

## 服务器更新与诊断

```bash
cd /opt/rift-ledger/rift-ledger-go
bash scripts/update.sh
bash scripts/telegram-diagnostics.sh
```

诊断脚本自动进入源码根目录，检查宿主机/容器的IPv4 DNS、无Token HTTPS、容器内健康接口、队列状态数量和限流等待秒数。只读，不修改DNS、防火墙、数据库、机器人配置或群权限，不输出玩家明细。它用于收集证据，不会把任意HTTP响应或`healthy`等同于机器人可收发。

判断顺序：

1. 宿主机可连、容器不可连：重点看容器DNS、代理、路由及转发；DNS结果不同本身不能单独证明错误，不固定写死Telegram IP。
2. 两边HTTPS都可连：查看后台接收错误、身份冲突、群权限和具体发送记录。
3. 显示限流等待：等待到期，不重复点击测试发送或重启尝试绕过。
4. 出现UNKNOWN：先在目标会话核实送达，再使用已有“已核实/重试”处理；不要为补发重复开奖。
